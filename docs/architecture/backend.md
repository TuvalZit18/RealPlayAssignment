# Backend (mocked)

Status: approved · Related: [api.md](api.md), [testing.md](testing.md)

There is no real backend. The API is mocked with **MSW (Mock Service Worker)**, which intercepts `fetch` calls in the browser and answers them.

## Why MSW

- The app makes real HTTP requests, so reviewers can inspect the `POST /api/register` body (including attribution) in DevTools → Network.
- App code is production-shaped: removing MSW and pointing `VITE_API_BASE_URL` at a real server is the only change needed.
- The same handlers run in Vitest through `setupServer`, so tests and the running app share one mock.

Rejected: an in-app fake function (no visible request, app code differs from production) and a separate local server (a second process to run for a front-end task).

## Files

| File | Purpose |
| --- | --- |
| `src/mocks/handlers.ts` | Request handlers. The single definition of mock behaviour |
| `src/mocks/browser.ts` | `setupWorker(...handlers)`, started in `main.tsx` before render |
| `src/mocks/server.ts` | `setupServer(...handlers)`, started in `src/test/setup.ts` |
| `public/mockServiceWorker.js` | Generated by `npx msw init public --save`; committed. `--save` records the folder in `package.json` so the file stays in sync when MSW is upgraded |

MSW runs in `dev` and `preview`. There is no production deployment.

MSW 3 notes: handlers import `http` and `HttpResponse` from `msw/http`, `delay` from `msw`. The unhandled-request option is `onUnhandledFrame` (`'bypass'` in the browser, `'error'` in tests). The v3 Vite plugin (`msw/vite`) is not used; it relies on an experimental API and is meant for dev only.

## Handler behaviour: `POST /api/register`

1. Wait about 600 ms, so the pending state is visible (0 ms in tests).
2. Validate the body against the rules in [api.md](api.md). Invalid → `400`.
3. If the email is `fail@example.com` → `500`, to demo error handling and confirm attribution is kept.
4. If the email was already registered since the page loaded → `409`.
5. Otherwise store the email in an in-memory set and return `201` with `{ user: { id, name, email }, token }`. `id` and `token` are random strings.

The in-memory set resets on every page reload, and when the app fires the `realplay:demo-reset` window event (the **Reset demo** button; see [auth.md](auth.md#reset-demo-reviewer-helper)). That is acceptable for a demo; the session itself lives in `localStorage` on the client.

## Dev helper

Each handled request is logged to the console (MSW default), showing the method, URL and status.
